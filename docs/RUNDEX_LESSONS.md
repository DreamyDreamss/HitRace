# Rundex 대조 개선 계획

작성 2026-08-01. `D:\Rundex`(Kotlin 154파일 / 35,641 LOC, Play 출시 v0.22.0)를 HitRace
(41파일 / 5,870 LOC, 미출시)와 대조해 뽑은 실행 계획.

Rundex는 **같은 사람이 만든, 이미 실사용자를 겪은 러닝 앱**이다. 거기서 이미 값을 치르고 얻은
교훈(가민 대비 1km 손실 신고, OEM 강제종료, 콜드 픽스 튐…)을 HitRace가 다시 겪을 이유가 없다.
반대로 Rundex의 부채(God-object 액티비티, 생 JSON 파싱, strings.xml 부재)는 **가져오지 않는다** —
HitRace의 타입 안전한 Retrofit + Compose 구조가 그 부분은 이미 낫다.

주의: 두 앱은 제품이 다르다. Rundex는 소셜 러닝 앱(피드·크루·팔로우·POI 도감), HitRace는
러닝 결과를 검으로 바꾸는 게임이다. **소셜 기능 전체를 베끼자는 계획이 아니다.** 아래는 제품
방향과 무관하게 "러닝을 기록하는 앱"이라면 반드시 있어야 하는 것들 위주다.

## P0 — 러닝 데이터가 유실되거나 왜곡되고 있다

### P0-1. GPS 원시 좌표를 필터 없이 그대로 받고 있다 ★최우선
`RunTrackingService.startLocationUpdates()`는 FusedLocation이 주는 **모든 픽스를 무조건**
`RunTracker.add()` 한다. 정확도 게이트도, 지터 게이트도, 평활도 없다.

이게 2026-07-31 `gps_jump` 거절의 진짜 출처다. 서버 쪽은 고쳤지만(이상치를 버리고 계속 진행),
클라이언트는 여전히 쓰레기를 만들어 보낸다. 게임이라서 더 나쁘다 — **거리가 곧 재화**이므로
정지 중 지터로 쌓인 유령 거리가 철광석·티켓·주조 스코어로 환산된다.

Rundex 대응(그대로 이식 가능, 순수 Kotlin·안드로이드 의존 없음):

| 파일 | 줄 | 역할 |
|---|---|---|
| `LocationFilter.kt` | 101 | 3단 게이트: 정확도(첫 픽스 20m/이후 25m) → 속도(>10m/s 폐기) → 최소이동(정지 지터). 30초 초과 공백은 새 앵커로 rebase |
| `GpsSmoother.kt` | 55 | 1차원 칼만 평활. 정지 시 지터 흡수, 이동 시 빠른 추종, 10초 공백 후 스냅 |

특히 `LocationFilter`의 `minMove`를 **정확도에 비례**시키는 부분(정확도가 나쁠수록 지터 진폭도
크다)과, 기기가 정지를 확신할 때(도플러 속도≈0) 정확도 전체를 노이즈 반경으로 보는 처리는
고정 임계로는 못 잡는 케이스다. 주석에 왜 그렇게 됐는지가 적혀 있으니 같이 옮길 것.

작업량: 두 파일 이식 + `RunTrackingService`에서 `offer()`/`process()` 경유 + 단위테스트.

### P0-2. 완주한 러닝이 네트워크 한 번에 사라진다
`RunSession.track`은 메모리 전용이고 업로드 재시도 큐가 없다. 지하 주차장에서 완주하면
6km가 그냥 없어진다. 진행 중인 러닝도 마찬가지 — `RunTracker`의 점 리스트는 프로세스가 죽으면
끝이다(포그라운드 서비스라 잘 안 죽지만 OEM에 따라 죽는다).

Rundex 대응: `PendingUploadStore.kt`(56줄, 디스크 JSON 큐 + localId 멱등) +
`UploadFlusher.kt`(23줄, 어느 화면에서 재개해도 큐를 비움). 서버는 이미 멱등 키 개념이
있으니(주간 목표 보너스의 crossing) 러닝 업로드에도 localId를 붙이면 중복 없이 재시도된다.

추가로 HitRace에만 필요한 것: **진행 중 러닝의 디스크 스냅샷**(N초마다 points를 파일에). 앱이
죽었다 살아나면 "이어서 기록할까요?" 복구. Rundex의 `ActiveRunStore.kt`가 이 역할.

### P0-3. 화면이 꺼지면 기록이 끊길 수 있다
매니페스트에 `WAKE_LOCK`이 없다. Rundex는 **PARTIAL_WAKE_LOCK**을 포그라운드 서비스와 함께
쓰고(도즈 대응), 거기에 더해 **배터리 최적화 예외 안내를 예외가 켜질 때까지 세션마다 재안내**
한다 — 삼성 등 OEM이 포그라운드 서비스를 그냥 죽여서 나온 대응이다.
(`docs/PRODUCTION_READINESS.md` 네트워크/안정성 절에 완료로 체크돼 있음.)

우리 에뮬레이터 검증은 화면 꺼짐까지 확인했지만, **에뮬레이터에는 OEM 킬러가 없다.**

### P0-4. HTTP 타임아웃이 없다
`ApiClient`의 OkHttp 빌더에 타임아웃 설정이 하나도 없다 → 서버가 응답을 안 주면 무한 대기,
주조 버튼이 영영 "주조 중…"에 머문다. Rundex `Http.kt`: connect 15s / read 30s / write 30s /
call 60s + `retryOnConnectionFailure`. 10줄짜리 작업인데 체감 차이가 크다.

## P1 — 게임 판정이 조작된 데이터로 이뤄지고 있다

### P1-1. 케이던스·심박을 앱이 지어내서 보낸다
`RunTracker.track()`:
```kotlin
cadence = pts.indices.map { 170.0 + sin(it * 0.6) * 3 },
heartRate = pts.indices.map { if (it.toDouble() / pts.size < 0.65) 152.0 else 120.0 },
```
이 값이 서버로 가서 `conversion.ts`의 `cadenceStability`(변동계수)로 계산되고, 그게
**검의 내구도**가 된다. `sin` 파형은 변동계수가 거의 일정하므로 **모든 실제 러닝의 내구도가
사실상 같은 값**이다. 스탯 4종 중 하나가 장식이라는 뜻이고, "당신의 주법이 검이 된다"는 컨셉의
근거가 없다.

선택지 두 가지 — 어느 쪽이든 지금보다 낫다:
1. **걸음 센서**(`TYPE_STEP_DETECTOR`)로 실제 케이던스. Rundex `MotionGuard.onStep()`이 이미
   이 이벤트를 받고 있다. 심박은 대부분의 폰에 없으니 미보유로 보내고 서버가 중립값을 쓰게 한다.
2. **Health Connect 연동**(Rundex `HealthImport*.kt` 4파일 + `HealthConnectSyncWorker`).
   워치가 있으면 실제 HR·케이던스가 들어온다. 부수 효과로 **과거 러닝 임포트**도 된다 —
   신규 유저가 첫날부터 검을 여러 자루 가질 수 있어 온보딩이 훨씬 낫다.

당장은 (1), 여력 되면 (2). **어느 쪽도 못 하면 최소한 가짜 데이터를 보내지 말 것** —
서버가 데이터 없음을 알고 중립 처리하는 편이, 지어낸 값으로 스탯을 만드는 것보다 정직하다.

### P1-2. 탈것 감지를 서버만 하고 있다
서버 `vehicle_suspected`는 러닝이 끝난 뒤에야 터진다 — 30분 달리고 나서 "탈것으로 판정"을
보는 최악의 UX. Rundex `MotionGuard.kt`(61줄)는 **달리는 중에** 창 평균 속도로 판정해
자동 일시정지한다. 여기 달린 주석이 값진 교훈이다:

> 걸음수 기반 약한 규칙은 거리를 동결하지 않는다. 걸음 센서가 주머니/암밴드/배칭 지연으로
> 과소 보고되면 정상 러닝(특히 빠른 페이스)을 탈것으로 오판해 거리를 깎았다(가민 대비 ~1km
> 손실 신고). 그래서 자동정지는 러너가 절대 낼 수 없는 명백한 고속(8m/s≈28.8km/h)이 10초
> 이상 지속될 때만 발동한다.

**우리 서버의 `vehicle_suspected` 임계(10m/s 구간이 15% 초과)는 이 교훈을 반영하지 않았다.**
빠른 러너 + GPS 노이즈로 오탐이 날 수 있다. 임계 재검토 대상.

## P2 — 계정과 출시

### P2-1. 익명 로그인 데이터 이관 — 열린 결정 #2의 답이 Rundex에 이미 있다
지금 HitRace는 같은 이름으로 로그인해도 매번 새 계정(`demo_3c90`)이고, 앱을 지우면 검이
사라진다. Rundex는 **옵션 C**로 풀었다(`docs/GOOGLE_LOGIN.md`):

- 익명 세션은 그대로 유지(비회원 이용 가능)
- 설정에서 구글 로그인 → Credential Manager → ID 토큰 → Supabase `id_token` grant
- **`rpc/claim_anonymous_data(p_from)`** 로 익명 계정이 쌓은 데이터를 구글 계정으로 이전
- 보안: 소스가 **익명 계정일 때만** 이전 허용(로그인 계정 탈취 방지). 함수=트랜잭션이라 충돌 시
  전체 롤백

문서에 Google Cloud Console 설정 절차와 SHA-1 등록까지 다 적혀 있다. HitRace는 백엔드가 같은
Supabase라 **거의 그대로 적용된다.** 열린 결정 #2를 여기서 닫을 수 있다.

⚠️ Rundex 문서의 경고도 같이 가져올 것: 이미 데이터가 있는 구글 계정으로 재로그인하면 unique
제약 충돌로 claim이 롤백될 수 있다(익명 데이터는 안전하게 남음). 스테이징 검증 권장.

### P2-2. 출시 체크리스트를 처음부터 들고 갈 것
`docs/PLAY_SUBMISSION_CHECKLIST.md`는 실제 심사를 통과한 앱의 목록이다. HitRace에 없는 것:

- 인앱 약관 3종(개인정보·서비스·**위치기반서비스**) — 위치 앱은 위치기반서비스 약관이 별도 필수
- **인앱 계정·데이터 삭제**(`delete_my_account` RPC) — Play 필수 요건
- 위치 권한 요청 **전** 눈에 띄는 고지, 접근권한 안내 팝업(정보통신망법)
- 개인정보처리방침 **공개 웹 URL**(인앱 문서만으론 심사 불가)
- Data Safety 양식, 포그라운드 서비스 권한 선언(유형=위치)

이건 "나중에"가 비싼 항목이다. 계정 삭제 하나만 해도 서버 스키마 20개 테이블의 정리 순서를
따져야 한다 — 테이블이 더 늘기 전에 지금 만드는 게 싸다.

### P2-3. 크래시 로그가 남지 않는다
Rundex `CrashReporter.kt`(37줄) — 전역 핸들러로 마지막 스택트레이스를 디스크에 남기고 시스템
기본 핸들러에 위임(크래시를 삼키지 않음). "HitRace 앱이 계속 중단됨"을 사용자가 겪었을 때
우리가 확인할 수 있는 게 지금은 아무것도 없다.

## P3 — 러닝 앱으로서의 완성도

- **지도가 없다.** HitRace는 경로를 Canvas 폴리라인(`RouteTrace`)으로만 그린다. 어디를
  달렸는지 알 수 없다. Rundex는 MapLibre + OpenFreeMap 타일.
  단, `PRODUCTION_READINESS.md`의 경고를 반드시 같이 읽을 것: 지도 타일·주소검색(Nominatim)·
  보행경로(OSRM 데모)·고도(Open-Meteo)가 전부 **SLA 없는 무료 공개 서버**이고, 사용자가 늘면
  레이트리밋/차단 위험이다. 렌더 엔진(MapLibre)은 그대로 두고 **데이터 제공자만 교체**
  가능하게 설계하라는 게 Rundex가 도달한 결론이다. 처음부터 그렇게 만들면 된다.
- **GPX 내보내기/가져오기**(`GpxExporter`/`GpxImporter`) — 다른 앱에서 넘어오는 러너의 이탈 방지.
- **오프라인 감지**(`Net.isOnline`) — 지금은 어떤 실패든 "문제가 발생했습니다". 오프라인과
  서버 오류는 사용자가 할 일이 다르다.
- **고도**: HitRace는 GPS 고도를 그대로 쓴다(오차 큼). Rundex는 `ElevationClient`(Open-Meteo)로
  보정하고 `ElevationGain`으로 노이즈를 걸러 상승고도를 낸다. 고도가 주조 스코어에 들어가므로
  정확도가 곧 공정성이다.

## Rundex에서 **가져오지 않을** 것

`docs/ARCHITECTURE_REVIEW.md`가 자기 부채를 정직하게 적어놨다. 우리가 반복하지 말 것:

- **God-object**(ApiClient 1188줄/200메서드, CrewDetailActivity 3370줄) — 네트워크+파싱+상태+UI 혼재
- **모델 부재** — 화면마다 생 JSONObject `optString`/`optDouble` 산재.
  HitRace는 kotlinx-serialization 타입 모델을 쓰고 있으니 이 점은 이미 낫다. 유지할 것.
- **평면 패키지** 154파일 단일 패키지. HitRace는 `data/ui/service/ui.screens`로 나뉘어 있다. 유지.
- **strings.xml 부재** — 한국어 전량 인라인이라 i18n 불가(열린 결정 #8과 직결).
  HitRace도 **지금 똑같이 인라인**이다. 5,870 LOC인 지금이 옮길 마지막 기회다.

반대로 Rundex의 이 규칙들은 지금 채택할 가치가 있다(`CLAUDE.md`):
- **DB는 가산·비파괴만.** 기존 RPC 시그니처를 drop/변경하지 않는다.
- **UI에 이모지 금지**, 텍스트 라벨·기호만.
- 디자인 토큰을 `colors.xml` ↔ `values-night` 페어링으로 완전 이중화(846회 참조).
  HitRace의 `Rb` 토큰 오브젝트가 같은 역할을 하지만 **다크 단일 테마 전제**다. 라이트 모드나
  시스템 폰트 스케일 대응은 아직 없다.

## 실행 순서 제안

1. **P0-4** HTTP 타임아웃 (10줄, 30분)
2. **P0-1** LocationFilter + GpsSmoother 이식 (반나절) ← 오늘 겪은 버그의 뿌리
3. **P0-2** 업로드 큐 + 진행 중 러닝 스냅샷 (하루)
4. **P0-3** WakeLock + 배터리 최적화 안내 (반나절)
5. **P1-1** 걸음 센서 케이던스, 없으면 가짜 데이터 전송 중단 (반나절)
6. **P2-3** CrashReporter (1시간)
7. **P1-2** MotionGuard + 서버 `vehicle_suspected` 임계 재검토 (반나절)
8. **P2-1** 구글 로그인 + `claim_anonymous_data` (하루, 결정 #2 필요)
9. **P2-2** 출시 체크리스트 (약관·계정삭제 RPC가 큰 덩어리)
10. **P3** 지도·GPX·고도 보정 (제품 판단 필요)

1~7은 결정을 기다릴 필요 없이 진행 가능하다. 8~10은 사용자 결정이 필요하다
(`docs/OPEN_DECISIONS.md` #2 인증, #6 스토어, 지도 제공자 비용).
